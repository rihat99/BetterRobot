Time is spent launching tiny operations, not computing

On a GPU every torch operation costs about 20 microseconds to launch, however small the data. One forward kinematics (FK) call on a 25-joint body launches about 220 of them. So the call takes milliseconds at batch 1 and almost the same at batch 4096. The CPU shows the same fixed cost at small batch:

Measured in this session at commit 7e2008f, float32, eager torch 2.13, AMD EPYC 9654. Batch 64 does 64 times the work of batch 1 for 1.7 times the time: the rest is fixed overhead.

The cause is in the code. FK, RNEA, CRBA, ABA and the centroidal pass each loop over joints in Python, one joint at a time. Only the Jacobian pass was rewritten to treat all joints at once; it needs 52 operations for any robot.

Batched IK inherits this: with default settings on Panda at batch 1024, one solve took 4.2 seconds on CPU. Only 67.5% of the elements reached the default tolerance of 1e-6 within 100 iterations, although every target was reachable, and the slowest element sets the time for the whole batch. The final errors were not recorded, so this may be a tolerance too tight for float32 rather than failed solves.

GPU timings are missing. All eight GPUs were busy during this session. Operation counts below are exact; GPU times are marked indicative. Clean GPU baselines are the first task of phase P0.

Warp speeds up the forward pass of two algorithms and nothing else

  • Only FK and RNEA have a Warp version: 2,206 lines, each kernel written twice (float32, float64).
  • The backward pass re-runs the torch implementation (kinematics/_warp_bridge.py:38). Its own comment says Warp's generated gradient is wrong for the tree loop. Optimization and learning need gradients, so they gain nothing.
  • Joint types are dispatched in three places: torch joint classes, a 22-branch switch in the Warp FK kernel, lookup tables in the Warp RNEA kernel.
  • Stored numbers from an older commit (25-joint body, forward only): Warp 0.54 to 0.63 ms, compiled torch 0.71 to 1.42 ms. Both are flat from batch 1 to 4096, so the gap is fixed overhead, not throughput.

For anything that needs gradients, Warp should therefore be no faster than torch alone. That comparison was never measured; it is experiment E1 below. Making Warp the single implementation instead would mean hand-writing gradients for about eight algorithms, including gradients with respect to link lengths and inertias that BetterHuman needs for body shape, and it would lose torch.func and double backward. That is several thousand lines for a gain nobody has measured.

The rule: each algorithm has an operation budget, checked automatically

A tree can be processed level by level: all joints at the same depth are independent, so one batched operation handles the whole level.

The plan applies three changes to every pass:

  1. Compose per level instead of per joint (FK, ABA). For RNEA, CRBA and the centroidal pass, replace the recursion by sums over precomputed ancestor and descendant index tables.
  2. Shrink the constant part. On small robots most operations are not in the chain at all: input preparation, one code path per joint type, building 4x4 matrices, converting matrices to quaternions. Keep poses as rotation plus translation, use one batched formula per joint family, and convert to quaternions only at the public boundary.
  3. Count operations in CI. For a fixed torch version the count is exact and has no timing noise, so a regression fails a test on any machine.

The budget is a constant for passes that are sums over index tables (the Jacobian pass today: 52) and grows with tree depth for passes that must go level by level (the FK chain, ABA). Index tables cost memory: a 200-joint body has about 4,000 ancestor pairs, and one 6x6 float32 tensor per pair at batch 4096 is about 2.4 GB. So each pass also gets a memory budget, and a pass that breaks it stays level-wise.

On top of that, one optional wrapper compiles the same functions (torch.compile, CUDA graphs). It is an accelerator, never a second implementation.

Prototype: level batching pays on large trees and on gradients

A 60-line prototype replaced only the per-joint chain in FK. Results are bit-identical to the library.

  • 223 joints, forward + backward on a busy GPU (indicative): 52 ms to 13 ms at batch 1, 72 ms to 38 ms at batch 4096. On CPU at batch 4096: 2.55 s to 0.64 s.
  • 25 joints, forward: no change. About 200 of the 220 operations are the constant part of change 2 above. Small robots and arms gain only from change 2, which has no prototype yet. It is the first prototype of P0.
  • torch.compile gave no gain on the 223-joint forward pass. The accelerator needs its own experiment.
  • A variant that composes ancestors in log(depth) steps used the fewest operations but was 2.4 times slower at batch 4096. Per-level is the better default.

Warp is removed when one measurement confirms the argument

The recommendation is to delete Warp. The honest status: the argument (its backward is torch, so it cannot help when gradients are needed) is read from the code, not measured, and today's torch forward pass is slower than Warp's stored forward time (2.3 to 2.6 ms against 0.54 to 0.63 ms on a 25-joint body, on different GPUs). So forward-only users would lose speed until the rewrite lands. That trade is your call.

A smaller model layer underneath

  • Model = structure + values. Structure is topology and index tables. Values are differentiable tensors that can carry batch axes (one body shape per subject). One model.replace(gravity=..., joint_placements=...) covers all 15 value fields; today with_values covers 3.
  • Results instead of a cache. state = kinematics.forward(model, q) returns an immutable object; Jacobian and dynamics functions take it. It holds everything later passes need (world poses, joint axes, velocities if given), so nothing recomputes FK. This removes 26 optional cache fields and the stale-cache hole.
  • One joint registry. A joint family is one entry with one batched formula. Adding a joint type touches one file instead of six.
  • Geometry is typed. Visual and collision shapes become a real object on the model, not an entry in a meta dict.
  • The public API is what downstream uses. build_tree, JointKind, Model.expand_q become public; a test in BetterHuman fails on any private import.
  • Remove what is not real. Unused spatial wrapper classes go. The collision stubs are replaced in P2 by a minimal real module (sphere and capsule pairs, sphere against a distance field), because trajectory optimization is judged with obstacles.
