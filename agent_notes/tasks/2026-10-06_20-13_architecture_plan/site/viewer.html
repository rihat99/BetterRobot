The three share no code. Each draws a skeleton as one sphere per joint and one cylinder per bone, each has its own quaternion conversion and its own colors. The best ideas are split: BetterHuman has the cleanest abstraction (a layer owns a group of scene objects and updates them), BVR has the best mechanics (one update per frame, a real playback clock, skinning done in the browser). BetterRobot's viewer has the most interface for the least function: a backend protocol with one backend, and several functions nobody calls.

Stay on viser; the missing piece is small

viser is the library all three viewers already use. Version 1.0.30, installed in BVR's environment, was probed in this session. It has every drawing primitive the plan needs: skinned meshes, batched meshes with per-instance color, arrows, coordinate frames, camera frustums, point clouds, drag handles, plots, one atomic update per frame, and a scene recorder. It runs on the GPU server and is viewed from a laptop or phone browser, which is how you work.

The one thing viser lacks is a timeline. That is about 150 lines of our own code, and BVR already has a working version.

Limits of this comparison. viser was checked by running code. The other libraries were judged mostly from prior knowledge, with a few web checks. The conclusion does not hinge on them: the plan keeps the data in plain arrays, so a second output can be added without touching the core.

Three core types: Viewer, Timeline, Layer

  • Layer. One kind of visual with its data for all frames. Four methods: build, set_frame(k), set_visible, and an optional own control panel. A single pose is simply T = 1.
  • Timeline. Current frame, play, pause, scrub, speed, loop. Skips frames by wall clock when the link is slow.
  • Viewer. Holds the server, puts layers into named groups (one person, one robot, one clip), and pushes frame k to all visible layers in one atomic update.

Interactive tools (an IK drag handle, picking, BetterHuman's editors) are separate objects that hold a viewer and callbacks. This reverses today's dependency: the viewer no longer imports the IK solver; the IK example uses the viewer.

What using it looks like

Sketches of the target API.

# a robot trajectory, joints colored by torque, torque plot beside the 3D view
viewer = Viewer()
viewer.add(robot_layers(model, q_traj, skeleton=True, tau=tau_traj))   # (T, nq), (T, nv)
viewer.add_plot("tau", tau_traj, labels=model.joint_names)
viewer.play()

# a human clip: mesh, skeleton, contact forces
viewer = Viewer()
viewer.add(human_layers(body, identity, q_seq), group="person0")
viewer.add(ArrowsLayer("contacts", origins=cop, vectors=grf, scale=1e-3), group="person0")
viewer.play()

# two solutions side by side
for name, q, dx in [("reference", q_ref, 0.0), ("ours", q_ours, 1.0)]:
    viewer.add(robot_layers(model, q, offset=(dx, 0, 0)), group=name)

viewer.save("clip.viser")      # a file that plays in any browser, no Python
viewer.record("clip.mp4")      # needs one open browser tab; slow

Six rules keep playback smooth

  1. Compute once. An adapter runs FK for the whole clip on the GPU and converts to arrays once.
  2. Batched objects. A skeleton is two batched objects (all spheres, all bones), not one object per joint. Messages per frame scale with the number of layers, not people times joints.
  3. Skinning in the browser. Send bone poses per frame, never vertices.
  4. One atomic update per frame.
  5. Fixed sizes. Nothing is created or removed during playback; unused items are hidden.
  6. Heavy per-frame data (video frames, per-frame point clouds) is read on demand through a small cache.

Rules 2 and 6 fix the two limits measured in BVR's viewer today: one message per sphere and bone, and one scene object per frame for point clouds.

What moves and what is deleted

TodayAfter
BetterRobot viewer, 1,872 linesNew core, about 1,600 lines: viewer, timeline, 10 layers, robot adapter, gizmo and picking tools, export, one theme. Backend protocol and mode registry are deleted.
BetterHuman studio and viz, 3,263 linesAbout 400 lines of human layers on the core. The editors you still use stay as a BetterHuman app, about 1,200 lines.
BVR viewer, 2,871 linesBVR keeps its file loaders and turns a clip into core layers. Its 990-line scene class becomes a list of layers.

Order: core and robot adapter first, with the four scenarios above as tests; then BetterHuman's layers; then BVR; then delete the old code. One shared theme (colors, lights, panel layout) replaces three sets of hard-coded constants and gives all three a consistent modern look.

Not yet measured

  • Websocket throughput: four people and two robots at 30 frames per second, on a phone or over VPN. A small benchmark comes before the layer design is frozen.
  • The maximum bone count of viser's skinned mesh (matters for the 200-joint MHR body).
  • File size of a recorded .viser scene for a long clip.
  • viser has no true headless video rendering. If you need videos from batch jobs with no browser, that is a separate offline renderer reading the same arrays (decision 7 on the overview page).
