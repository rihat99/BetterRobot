Today: a third of BetterRobot is an optimization stack nobody downstream uses

BetterRobot has 24,070 lines of source. The three packages that make up optimization (optim, residuals, tasks) hold 8,509 of them. BetterVideoReconstruction (BVR), the main project built on the library, imports none of the three. It carries its own 193-line engine on top of torch.optim.

BetterHuman has 7,345 lines. Its core idea works well: compute everything that depends on body shape once, then stream poses through BetterRobot's kinematics. But 43% of the package is an editing studio that is a second, separate viewer.

Five problems, each backed by a measurement or a line of code

1. The optim API cannot express what real fitting code needs

BVR's fit uses about 38 loss terms. Most are robust scalar losses, switched on and off by stage, with some variables frozen in some stages, under Adam first and L-BFGS later. The library wants every cost as a fixed-width residual object attached to variable objects. A scalar loss has to be disguised as a sqrt(2f) row. There is no public way to write a new optimizer: the built-in ones reach into 18 private members of Problem. solve_ik cannot take one extra cost.

2. Warp is a second implementation that only speeds up half of the work

Only forward kinematics (FK) and inverse dynamics (RNEA) have a Warp version. The backward pass of both re-runs the torch code, so gradients gain nothing. Jacobians, mass matrix, forward dynamics have no Warp version at all. The price is every formula and every joint type written two or three times.

3. The library is slow because it does many tiny operations

One FK call on a 25-joint body launches about 220 small GPU operations, and about 800 with the backward pass. Each costs roughly 20 microseconds whatever the batch size. That is why time barely changes between batch 1 and batch 4096 on GPU, and why a second backend does not fix it. Details on the Speed page.

4. Three viewers, each with half of the features

BetterRobot's viewer shows one pose. BetterHuman's studio edits one pose. BVR's viewer plays clips with forces, cameras and several people, but is tied to BVR's file formats. None can show collision geometry, export a video or plot a signal next to the 3D view.

5. The foundation has grown special cases

  • Model has 57 one-line forwarding properties. Changing gravity needs a nested dataclasses.replace.
  • Data is a mutable cache with 26 optional fields and a documented way to go stale.
  • Joints are described twice (classes and numeric codes). A new joint type touches 6 files.
  • collision is all stubs. The spatial classes are not used by the algorithms.
  • BetterHuman and BVR import private modules, so the real API is about twice the declared one.
Three bugs found during the audit
  • lie/tangents.py:187: the SE3 Jacobian series stops after the 9th power. The comment says this is exact for errors up to 6; at a pose error of 3.5 the next term is about 0.007. The analytic IK Jacobian is therefore wrong far from the target (measured error 0.005 to 0.04) and right near it.
  • random_configuration returns float32 on a float64 model, and infinity for revolute joints without limits.
  • FK with a float64 model and a float32 input crashes deep inside instead of reporting the mismatch.

The pinocchio comparison tests would have caught the first bug, but pinocchio is not installed in the dev environment, so those tests skip silently.

What the new optim looks like for a user, in full:

P = optim.Problem({"q": q0}, manifolds={"q": RobotManifold(model)})
P.residual("pose", lambda q: pose_error(model, q, target))
P.residual("rest", lambda q: q - q_rest, weight=0.01)

x = optim.solve(P, optim.LM(), iters=30).x            # second order
x = optim.solve(P, torch.optim.Adam, lr=1e-2, iters=500).x   # or any torch optimizer

Nine decisions that are yours

Each has a recommendation. None blocks P0.

  1. Remove Warp once a measurement confirms it gives nothing when gradients are needed, accepting slower forward-only calls at small batch until the rewrite lands? Recommended: yes.
  2. Replace the mutable Data cache by immutable results (state = forward(model, q))? Recommended: yes.
  3. Costs read variables by argument name (lambda q, betas: ...)? It is short but fragile with partial and renames; the alternative is to always list reads=. Recommended: by name, with a loud check at registration.
  4. Is batch 65,000 and above a real use case (sampling, reinforcement learning)? Only there does a hand-written GPU kernel pay off.
  5. Retargeting lives in BetterHuman (recommended) or in a third package?
  6. Which studio editors do you still use: segment painting, contact frames, posing?
  7. Do you want video rendering without a browser, or a rerun exporter? Both are optional add-ons.
  8. Facial expression exact (recommended) or approximate? Next body family: SKEL or STAR/SUPR?
  9. Order after P0: optim first (recommended), or speed first?

What was checked and what was not

  • Checked against code: all line counts, the Warp backward path, the Jacobian series bug, what BVR imports.
  • Measured in this session: CPU timings of FK, Jacobian, RNEA, CRBA, ABA and IK; GPU operation counts; a level-batched FK prototype; seven ways of automatic Jacobians through the library's FK.
  • Not measured: clean GPU timings. All eight GPUs were busy, so GPU times on these pages are marked as indicative. No fresh Warp or pinocchio numbers. Nothing was run for BetterHuman; its numbers come from its own docs.
  • Estimates: target sizes in lines and the speed targets. They are goals to test in P0, not results.
  • Reviewed: an independent reviewer with no knowledge of this session attacked the plan: 17 findings, 2 critical. All but one were accepted and are folded into these pages. The record is in DESIGN.md, section 5.
