The core idea stays: bake shape once, then stream poses

None of the reference human libraries (smplx, MHR, SOMA, anny) offers dynamics with per-subject differentiable inertias. That is BetterHuman's real advantage and the plan protects it. Also kept: the pure tensor pipeline, the parity tools (vertex error against upstream is 6e-7 m for the SMPL family and 1.4e-6 m for MHR), and the file schema.

Five debts

  1. A second viewer. 43% of the package is the studio, a separate viser application. See the Viewer page.
  2. Private imports. BetterHuman reaches into four BetterRobot internals (the tree builder, the frame record, the reduced-coordinate expander, the joint code table). Any refactor of BetterRobot breaks it.
  3. Slower than upstream. BetterHuman's own stored table shows its torch path 1.1 to 2.5 times slower than upstream smplx (SMPL at batch 1: 3.93 ms against 1.55 ms), even with shape baking excluded. The cause is BetterRobot's FK overhead, the subject of the Speed page.
  4. Expression forces a re-bake. SMPL-X facial expression is treated as shape, so a clip with changing expression repeats the whole bake every frame, including a Python loop over body parts for inertias.
  5. Behaviour hidden in stored functions. A body is assembled from policy callables and cloned with object.__new__. Families disagree: MHR's converter returns two values, SMPL's one. Only 3 families are registered.

Missing altogether: retargeting, marker sets, pose priors, joint limits, a ground contact model, and human cost terms for optimization. BVR wrote several of these itself.

Source of these numbers. Nothing was run for BetterHuman in this session: the dev checkout has no model files and its benchmark needs a free GPU. Timings come from docs/contracts.md in the repository, GPU unknown.

Target: families as data, three verbs, public API only

PieceWhat it is
FamilySpecPure data for one body family: template mesh, shape and expression bases, joint regressor, skin weights, kind of pose corrective, landmark and contact sets. Per-family behaviour is an enum plus arrays, not stored functions.
BodyThe static model for one family. Holds the BetterRobot Model structure.
body.bake(betas=...)Returns an Identity: per-subject values, differentiable, with batch axes.
body.forward(identity, q, stream=..., outputs=...)Per-frame work. stream carries per-frame inputs such as expression. outputs selects joints, markers or full vertices.
  • Cheap new families. SMPL-H and MANO become a table and a short loader because they share SMPL's math. STAR and SUPR add one sparse corrective kind. SKEL (a biomechanical skeleton) needs non-spherical joints, which BetterRobot already supports.
  • Expression without re-baking. At bake time, precompute how the expression coefficients move the joints (a small matrix). Per frame only joint placements change; inertias stay. This is exact, and needs BetterRobot's FK to accept placements that vary over time, which is part of phase P2.
  • Ask for less. A keypoint fit needs a few dozen markers, not 10,475 vertices. Skinning only the requested points is 50 to 100 times less work, and one SMPL-X vertex tensor for 10,000 frames is 1.26 GB.
  • Public API only. BetterRobot exposes what BetterHuman needs (build_tree, JointKind, Model.expand_q, batched value replacement, FK returning rotation matrices). A test in BetterHuman fails on any other import.
  • Human terms on the new optim. Pose prior, joint limits, markers, 2D reprojection, ground contact and foot skate, as plain functions.
  • Inverse dynamics with contact. Solve the floating-base rows for contact forces per frame, read joint torques from the rest, report the leftover wrench.
  • Retargeting in better_human.retarget. Built only from BetterRobot's public tasks and optim, with a source-agnostic input (named frames over time), so it can move to its own package later if needed.
  • Viewer. About 400 lines of layers on BetterRobot's viewer. The studio shrinks to its editors.

What using it looks like

Sketches of the target API.

import better_human as bh

body = bh.load("smplx", path, gender="neutral")
ident = body.bake(betas=betas)                               # once per subject
out = body.forward(ident, q, outputs=bh.Outputs.VERTICES)    # q: (B, nq)
out.vertices                                                 # (B, 10475, 3)

# fit a body to 3D keypoints over a clip
P = optim.Problem({"q": q0, "betas": b0}, manifolds={"q": RobotManifold(body.model)})
@P.cached
def posed(q, betas): return body.forward(body.bake(betas=betas), q, outputs=bh.Outputs.MARKERS)
P.residual("keypoints", lambda posed: (posed.markers - kp3d) * conf)
P.residual("prior",     bh.terms.pose_prior(body))
P.residual("smooth",    temporal.diff("q", order=2))
result = optim.run(P, [optim.Phase("root", ...), optim.Phase("full", ...)])

# inverse dynamics with contact forces
dyn = bh.dynamics.inverse_dynamics(body, ident, q, v, a, contacts=contact_mask)
dyn.tau, dyn.contact_forces, dyn.residual_wrench

# retarget the clip to a humanoid robot
q_robot = bh.retarget.retarget(body, ident, q, robot=g1_model, match=bh.retarget.G1_TABLE)

Speed plan: benchmark first, then four techniques

TechniqueExpected effectStatus
Fewer FK operations (from BetterRobot P2)FK at batch 1 from about 2 ms toward 0.5 msEstimate
FK returns rotation matrices, no quaternion round tripRemoves a conversion per callEstimate
Skin only requested points50 to 100 times less skinning work in keypoint fitsArithmetic
Top-K skin weights, sparse pose correctives (opt-in)Less memory and time at large batchFrom MHR, SOMA, STAR

Target, to be tested: SMPL-X forward at batch 256 at least as fast as upstream smplx (4.32 ms in the stored table). The benchmark suite comes before any speed work: every family, batch and clip length sweep, CPU and GPU, forward and backward, against upstream smplx and MHR, with results in a machine-readable file and a regression gate. Today the suite has no backward, CPU or memory rows.

Order of work

  1. BetterRobot makes the needed API public (part of P0 and P2).
  2. Benchmark suite and baselines.
  3. FamilySpec, Body, Identity; port SMPL, SMPL-X, MHR; parity tools keep guarding accuracy.
  4. Stream groups and output selection.
  5. Layers on the new viewer; studio reduced to its editors.
  6. Human terms, inverse dynamics with contact, retargeting (after the new optim, P1).
  7. New families: SMPL-H and MANO first because they are nearly free.
