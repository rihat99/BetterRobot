The current optim asks the user to learn a graph before writing one cost

To solve IK with one custom cost today, a user needs 9 or 10 concepts: Variable, RobotVariable, Residual with a fixed dim, Node and its lifetime rules, Problem, weights, a linearization mode, an optimizer class. A scalar loss must be wrapped so it looks like a residual. To use Adam, the cost goes through a wrapper that keeps its own hidden parameters.

BVR shows what users write when left alone: a 193-line engine with named tensors, costs as functions that return a number, values shared between costs and computed once, and stages that set a weight per cost. That engine is the real specification. The proposal keeps its shape and adds what it lacks: least-squares solvers, manifolds, Jacobians, batching.

Three thin layers; most users touch only the middle one

Five ideas to learn:

  1. Problem. A dict of named tensors to optimize, each with leading batch axes.
  2. Term. A plain function. Its argument names say what it reads. It is a residual (returns a vector; usable by least-squares solvers) or a scalar (returns a loss; usable by gradient solvers).
  3. Manifold. Only when a variable is not a plain vector: rotations, poses, robot configurations.
  4. Solver. Two functions, init and step.
  5. Phase. A stage of a fit: which weights, which variables are free, which solver, how long.

Each variable also declares its axes: independent batch axes, an optional time axis, or shared across time (body shape). Solvers keep batch elements independent and couple along time.

Robust kernels, bounds, weights and shared values are keyword arguments, not new concepts. P.loss(x) is an ordinary differentiable number, so a hand-written torch.optim loop works on it with no adapter at all.

Jacobians: automatic by default, analytic where it pays

The Jacobian of a term is a small dict: one block per variable the term reads, in tangent coordinates (the minimal coordinates of the manifold, so rotations and floating bases need no special handling). Three ways to get a block, tried in this order:

  1. The term supplies jac=. Built-in kinematic terms do, because the library already has frame Jacobians.
  2. Otherwise reverse-mode automatic differentiation of the term at a zero step on the manifold.
  3. optim.check_jacobian(term) compares 1 against 2 and against finite differences. It is a test tool, not a solver mode.

Measured in this session on the library's own FK (Panda and a 29-joint humanoid with floating base):

QuestionResult
Does automatic differentiation work through the current kinematics?Yes. Seven variants ran unchanged and agree to 1e-10.
How much slower than the analytic Jacobian?2 to 5 times on GPU (indicative, shared GPU); up to 11 times on CPU at batch 4096.
Which variant should be the default?Reverse mode: a pose error has 6 rows and many more columns.
Share of a Gauss-Newton step spent on the Jacobian?Most of it; a full step is 2.6 to 9.6 times slower with automatic Jacobians.

So the rule is: user-written terms get automatic Jacobians and work at once; the terms the library ships for kinematics carry analytic ones for speed.

Shared values are computed inside the differentiated call

Several terms usually read the same FK result. Two naive designs fail here. If each term is differentiated on its own, FK runs once per term. If FK is cached outside the differentiated call, the Jacobian through FK comes out as zero without any error. The design therefore linearizes the whole problem in one traced evaluation: cached values are pure functions of the variables, computed once inside the call, and all automatic terms are differentiated together. Analytic terms have the signature jac(values, cache) and read the same cached state. This was measured with one term only; a prototype with several terms sharing one FK is the first task of P1.

Details: trajectories, single precision, manifolds, constraints
  • Trajectories. A term that declares stencil=(-1, 0, 1) is written for one time window and evaluated on all frames at once. Its blocks give a block-banded system solved in time linear in the number of frames.
  • Single precision. Normal equations square the condition number. In the prototype a float32 Cholesky failed on a humanoid IK step until damping was raised. Policy: scale columns, keep a damping floor, and allow the linear solve alone to run in float64.
  • Manifolds. LM and Gauss-Newton step in tangent space and retract. torch.optim optimizes the raw tensor and projects after each step (re-normalizes quaternions), which is what BVR does today.
  • Mixed problems. Under LM, residual terms build the curvature and scalar terms add their gradient. A free variable that no residual term reads is an error under LM. A phase dominated by scalar terms should use Adam or L-BFGS.
  • L-BFGS. The batched version uses a fixed-budget backtracking line search per problem. Strong-Wolfe on one coupled problem stays available through torch.optim.LBFGS, which is what BVR uses.
  • Bounds and constraints. Box bounds by projection after each step. Augmented Lagrangian is a tested recipe with multiplier updates and a convergence check, used for collision and contact in trajectory optimization. General constraints come later.
  • Differentiating through the solution. mode="implicit" solves one linear system with the last Hessian. It is only valid at a converged solution away from the bounds, so it checks that and falls back to mode="unroll", which backpropagates through the steps.

A new optimizer is about 20 lines

A solver is two functions over a state of batch-first tensors. Every problem in the batch has its own damping and its own done flag, and nothing inside step waits for the GPU.

class SimpleLM(optim.Solver):
    def init(self, prob, x):
        loss = prob.loss(x)                               # (B,)
        return optim.State(x, loss, done=torch.zeros_like(loss, dtype=torch.bool),
                           extra={"lam": torch.full_like(loss, 1e-3)})

    def step(self, prob, st):
        H, g, _ = prob.linearize(st.x)                    # structured H, g: (B, N)
        dx = -H.solve(g, damping=st.extra["lam"])
        x_new = prob.retract(st.x, dx)
        loss_new = prob.loss(x_new)
        ok = (loss_new < st.loss) & ~st.done              # accept per problem
        lam = torch.where(ok, st.extra["lam"] * 0.3, st.extra["lam"] * 10)
        return optim.State(optim.where(ok, x_new, st.x), torch.where(ok, loss_new, st.loss),
                           done=st.done | converged(st.loss, loss_new), extra={"lam": lam})

Today the same job means subclassing a 530-line class and reaching into private members.

Left out on purpose

  • Variable objects, graph harvesting and Node classes. Dicts and names replace them.
  • General sparse linear algebra. Only dense and block-banded systems. Pose-graph problems with loop closures are out of scope.
  • Linearization modes and structure analysis. Structure comes from the stencil a term declares.
  • Riemannian Adam, QP, SQP, DDP.
  • A Schur solve for variables shared by all frames (body shape in a trajectory fit) until a prototype shows it is worth the code. First version: alternate, or leave shape to the gradient phases.

What this does for BVR, honestly

BVR's fit is first-order today: Adam, L-BFGS, robust scalar losses, no least-squares solver anywhere. The new layer first replaces its private engine with the same behaviour and adds manifolds, axis roles, logging and hooks. Levenberg-Marquardt on its dynamics stage is an experiment, not a promise. LM over body shape shared across all frames needs a solve that is deferred (see above).

Size: the design study estimates about 1,500 lines; the reviewer estimates 2,500 to 3,500 once all solvers and the banded solve are in. The commitment is under half of today's 4,019 lines and about 15 public names instead of 43.
